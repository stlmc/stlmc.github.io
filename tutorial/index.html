Checking Three Thermostat Properties

Check three nested STL properties of two networked thermostats over ten time units, then inspect a counterexample through temperature and robustness plots. The model starts at fixed temperatures $x_0=20$ and $x_1=18$ with both heaters off.

Model

Two rooms exchange heat through an open door. Each room has a heater, but the controller allows at most one heater to be on at a time.

Variables Meaning Initial state
x0, x1 Room temperatures, with declared range [10,35] x0 = 20, x1 = 18
on0, on1 Heater switches: 0 means off, 1 means on Both are off

The three modes are both heaters off, only the second on, and only the first on. Temperatures are continuous across mode switches and follow each mode’s ODEs between switches. on1 > 0.5 tests whether the second heater is on. The controller permits this heater to switch off once x1 >= 26; it does not require it to heat the room to 30.

Command-line Walkthrough

The following steps run the same example without the web workspace.

Download the Model

Download therm-tutorial.model into an empty working directory. For example:

The model declares three properties:

\[\begin{aligned} \textsf{f1} &= \square_{[0,8]}\lozenge_{[0,2]}(x_0\geq9),\\ \textsf{f2} &= \lozenge_{[0,2]}\square_{[0,8]}(x_1\geq9),\\ \textsf{f3} &= \square_{[0,5]}\bigl((\mathit{on1}>0.5)\Rightarrow\lozenge_{[0,1]}(x_1\geq30)\bigr). \end{aligned}\]

The inner interval is relative to the time selected by the outer operator:

Goal Outer time Inner requirement
f1: always eventually Every time $t$ in $[0,8]$ At least once during $[t,t+2]$, $x_0\geq9$
f2: eventually always Some start time $t$ in $[0,2]$ Throughout $[t,t+8]$, $x_1\geq9$
f3: always respond Every time $t$ in $[0,5]$ when heater 1 is on At least once during $[t,t+1]$, $x_1\geq30$

For example, f1 at time 3 examines $[3,5]$, not the fixed interval $[0,2]$. For f2, choosing start time 1 requires the condition throughout $[1,9]$. The first two properties follow from the declared temperature range $[10,35]$. The third asks whether every on-state of the second heater is followed within one time unit by a temperature of at least 30. This obligation applies at every time the heater is on, not just at its switch-on instant. For example, an on-state at time 3.5 requires a response during $[3.5,4.5]$. Because switching off is allowed from temperature 26, the controller need not meet this stronger response requirement.

The commands below use the downloaded file; you do not need to retype it.

Run the Checks

The checks use these settings:

Option Meaning in this walkthrough
-goal Select one of the three labeled properties
-bound 4 Limit the discrete STL partition, counting mode changes and STL variable points
-time-bound 10 Model an execution lasting ten time units
-time-horizon 10 Allow each continuous segment to last at most ten time units
-threshold 0 Check the property without requiring a positive robustness margin
-precision 0.000001 Set dReal’s separate numerical delta tolerance
-visualize Save data for later plotting or text inspection

One-step and two-step are alternative ways of solving the same bounded question. The choices below are for execution performance; they do not change the properties’ meanings. -parallel-core 4 limits the two-step workers to four.

Then check the heater-response goal and save its counterexample:

The global time bound is ten time units; time-horizon limits each continuous segment to at most ten time units. Neither is a wall-clock timeout. The discrete bound limits mode transitions and extra STL partition points, not elapsed physical time. Model comments do not set these analysis options.

With STLmc and the official dReal 3.16.06.02 binary, the first two commands report satisfied up to bound 4. The third produces the following counterexample result. The particular trace can vary between runs.

Goal Result Interpretation
f1 Satisfied up to bound 4 No counterexample to the first temperature check in this search
f2 Satisfied up to bound 4 No counterexample to the second temperature check in this search
f3 Violated at bound 2 The second heater is on, but its room does not reach 30 within the required response window

These queries use robustness threshold zero. dReal’s -precision 0.000001 sets its separate delta-decision tolerance; it is not the robustness threshold or an exact trajectory certificate. A result satisfied up to bound 4 means no counterexample was found within that bounded search, not an unbounded safety proof.

Inspect the Counterexample

When verification finds a counterexample, -visualize writes its data and configuration paths under artifacts in the terminal output. Use those actual paths: the filename contains the discovery bound, which can be smaller than the maximum bound supplied on the command line.

It shows one obtained trace; another run may choose different switching times. The graphs use reconstructed trajectories and sampled robustness, not an independent exact certificate.

Read the plots in this order:

  1. In the upper plot, follow the x1 temperature using its legend label: its slope changes from cooling to heating near time 3.23, then back to cooling near time 4.50. It reaches about 26 when the heater turns off, then cools again.
  2. In the lower plot, use the legend to inspect f3_5 (the on-state test) and f3_4 (the temperature-at-least-30 condition). An on-state at time 3.5 requires the temperature condition somewhere in $[3.5,4.5]$, but this trace stays below 30.
  3. Compare the full goal f3’s robustness at time zero with the red threshold line at zero. A negative value is the counterexample to the selected goal.

In this trace, the modes change from both heaters off to the second heater on at approximately $3.23$, then back to both off at approximately $4.50$. The heater-on interval lasts about 1.27 time units. Its temperature never reaches 30, so the required response fails even though the controller follows its permitted switch-off rule. Reconstructing the saved trace gives robustness $-0.5$ at time zero. Older pickle-based artifacts cannot be read by the current release; rerun verification to regenerate them.
